# 입력·출력 조건 종합 점검

- 점검일: 2026-10-26
- 기준: 현재 체크아웃 코드, README 기능 설명, HTML 입력 속성, Firestore 규칙, 기존 테스트. 별도의 확정 업무 명세가 없어 법정·노사협약 임금 산식 자체의 적법성은 판정하지 않았다.
- 결론: **기본 검사와 정상 경로 테스트는 통과하지만, 권한 제어와 시간·금액 경계값 문제 때문에 전체 정상 구현으로 판정할 수 없다.**
- 운영 코드·운영 데이터는 수정하지 않았다. 로컬 재현 스크립트와 이 보고서만 추가했다.

## 2. 발견 사항 — 우선순위순

### P0 / 근무일지·사용자 프로필 소유권 미검증

- 근거: `firestore.rules:152–196`, `public/js/app.js:6475–6542`.
- 요구: 본인 근무일지 및 비밀번호는 본인만 접근·변경, 전체 조회는 관리자 전용.
- 실제: `user_profiles` update는 로그인 여부·변경 필드·해시 형식만 확인하며 요청 UID와 프로필 소유자를 연결하지 않는다. 다른 닉네임의 비밀번호 해시 변경도 규칙상 허용된다.
- `work_logs` get은 인증만 요구하고, list는 workerId가 64자 이하 문자열이면 허용한다. update는 기존 workerId·날짜 보존만 요구한다. 이 조건들은 **요청자가 본인인지 증명하지 않는다**. 익명 인증 사용자도 포함된다.
- 영향: 타인 일지 조회·변경 및 프로필 비밀번호 교체 가능 경로. UI 비밀번호 확인만으로 방어할 수 없다.
- 조치: 서버 검증 인증과 ownerUid를 연결하고 읽기·쓰기 모두 소유권 강제. 기존 닉네임 자료의 소유권 마이그레이션 계획이 필요하다.
- 검증 수준: 규칙 정적 분석. 배포된 규칙 동일 여부 및 실제 공격 요청은 확인하지 않았다.

### P0 / 관리자 전용 긴급 공지를 일반 인증 사용자가 변경할 수 있는 규칙

- 근거: `firestore.rules:102–110`.
- 요구: 서버 PIN 검증을 통과한 관리자만 긴급 공지 작성.
- 실제: `isAdmin()`과 별개 OR 분기로 `emergency_notice`의 형식만 맞으면 create/update 허용. 서버 PIN 확인 결과가 Firestore 권한에 연결되지 않는다.
- 영향: 직접 SDK 호출로 공지 표시·내용 변경 가능 경로.
- 조치: 관리자 claim/UID를 규칙에서 강제하거나 인증된 서버 쓰기 API로 단일화. 정상 관리자 작성 회귀 테스트도 필요.

### P1 / 게시글·선박·댓글 수정 및 소프트 삭제에 작성자 검증 누락

- 근거: `firestore.rules:224–267`.
- 실제: 기존 password 해시를 유지하는 수정 또는 `isValidSoftDelete()` 형식만 충족하면 허용. 읽기가 열려 있는 문서의 해시를 그대로 유지하는 것은 비밀번호를 안다는 증거가 아니다.
- 영향: 타인 콘텐츠 변조·삭제 표시 가능 경로.
- 조치: 작성자 UID 또는 서버의 비밀번호 검증을 필수로 하고, 조회수 갱신과 내용 변경 권한 분리.

### P1 / 소수 시간 입력이 올림 계산되어 임금 과다 산정 — 로컬 재현

- 근거: `public/index.html:352–354` (`step="any"`), `public/js/app.js:6864–6902`.
- 입력: 평일 주간 1.5시간, 시급 10,320원, 가산 없음.
- 기대: 주간 1.5시간, 15,480원.
- 실제: `for (i=0; i<hours; i++)`에서 시간당 1씩 증가하여 주간 2시간, **20,640원**. 요약 총시간은 1.5시간이어서 출력 내부도 불일치.
- 조치: 시간 구간 교집합 또는 분 단위 적산으로 일원화. 0.5/1.5시간, 주야간 경계·자정·공휴일 경계 테스트 추가.

### P1 / 선박 스케줄의 분 정보가 임금 계산에서 사라짐 — 로컬 재현

- 근거: `public/js/app.js:3766–3800`.
- 입력: 동일 날짜 입항 08:45, 출항 10:15.
- 기대: 실제 경과 1.5시간(별도 정시 반올림 업무 규정이 없다면).
- 실제: 시각 문자열의 앞 두 자리만 추출하여 08시~10시, **2시간**. 08:15~08:45처럼 같은 시각대는 0시간으로 거절될 수 있다.
- 영향: 최대 4척 합산에서도 오차 누적. 보고서의 분 단위 적산과 계산기 기준도 다를 수 있다.
- 조치: 전체 타임스탬프 사용. 정시 절삭이 의도라면 입력·출력과 업무 명세에 명시하고 보고서에도 같은 정책 적용.

### P1 / 금액 입력의 유효성 검사 부족

- 근거: `public/js/app.js:6566–6599, 7009–7026`, `public/index.html:160,477`, `firestore.rules:184–194`.
- 음수 시급을 계산에 전달하면 음수 임금이 생성된다(로컬 함수 재현: -10,320원). 근무일지도 음수 금액을 저장 전 차단하지 않는다.
- `parseFloat(value) || 0`은 잘못된 값을 0으로 대체하고, 시급의 `|| 10320`은 0 입력을 기본 시급으로 바꾼다.
- Firestore는 임금 타입·유한성·범위·합계 일치를 검증하지 않는다. 보고서에는 총액을 0 이상으로 보정하는 경로가 있어 저장값과 출력값이 달라질 수 있다(`app.js:5643–5645`).
- 조치: 빈값/0/잘못된값 구분, 유한수·허용 범위·원 단위 정책 검증, 저장 계층에서도 합계 강제. 음수 정산 허용 여부는 업무 규정으로 확정.

### P2 / CSV 수식 주입 방어 없음

- 근거: `public/js/app.js:2317–2347`.
- 실제: 따옴표 escaping은 하지만 사용자 문자열의 수식 시작 문자 무력화가 없다. 메모 `=1+1`은 `"=1+1"`로 출력된다.
- 영향: Excel 등에서 수식으로 해석될 수 있다. 따옴표는 CSV 구문 보호일 뿐 수식 방어가 아니다.
- 조치: 사용자 텍스트의 `=`, `+`, `-`, `@`, 선행 제어문자 처리 정책 적용 또는 문자열 타입 XLSX 출력. 스프레드시트 프로그램별 확인 필요.

### P2 / 사진 처리 실패 시 저장 버튼 복구 누락

- 근거: `public/js/app.js:6637–6657`.
- 실제: 업로드 오류 콜백은 있으나 이미지 압축 Promise 및 `getDownloadURL()` 실패에는 catch/finally가 없다.
- 영향: 실패하면 버튼이 비활성화된 채 남고 저장이 끝나지 않을 수 있다.
- 조치: 압축→업로드→URL 획득→저장을 하나의 오류 처리 흐름으로 연결하고 모든 실패에서 버튼 복원.
- 검증 수준: 정적 분석, 실제 업로드 장애 주입 미실행.

### P2 / 스케줄 API 날짜 입력 검증 부족

- 근거: `server.ts:3823–3893`.
- 실제: 명시 startDate/endDate의 실존 날짜·순서·최대 조회 기간 검증이 없고, date도 정규식 형태만 확인한다.
- 영향: 잘못된 입력이 400으로 명확히 차단되지 않고 외부 조회·캐시 키로 전달되거나 기본 날짜로 치환된다.
- 조치: 공통 스키마로 실제 날짜, 시작≤종료, 조회 범위 제한 및 잘못된 입력의 400 JSON 응답 확정.
- 검증 수준: 정적 분석, 외부 터미널 실호출 미실행.

## 4. 미확인 영역과 권장 순서

- Firebase 운영 데이터·배포 설정·Storage 권한, 실제 메일·FCM·기상·터미널 연결은 확인하지 않았다. 외부 네트워크 제한과 운영 자격증명 미사용 상태에서 점검했다.
- 실제 브라우저 E2E 및 PNG/공유의 기기별 표시도 미실행. 이미지 내보내기 성공을 보증하지 않는다.
- 우선 **소유권/관리자 권한 결함**을 수정하고 Java 21 에뮬레이터에서 타인 조회·수정·비밀번호 교체·공지 변경이 거절되는 테스트를 추가한다.
- 다음으로 분 단위 산식과 입력 검증을 공통화하고 계산→일지→CSV→연간 보고서까지 같은 금액·시간인지 검증한다.
- 마지막으로 업로드 실패 복구, CSV 안전화, 날짜 API 검증 및 실환경 E2E를 수행한다.
