# BUSAN HAK PORT INFO 운영 런북

- 기준일: 2026-11-13
- 운영 애플리케이션: `https://busan-hak-port-info.vercel.app`
- Firebase 프로젝트: `busan-hak-port`
- 목적: 매일 확인할 사항, 배포 절차, 장애 대응, 데이터 보안·백업의 운영 기준을 한 곳에서 관리합니다.

> **중요 — 백업 보존:** Vercel은 임시 파일시스템을 사용합니다. `FIRESTORE_BACKUP_BUCKET`을 설정하고 업로드를 확인하기 전에는 Vercel 주간 백업이 영구 보존되지 않습니다. 이 저장소의 백업 엔드포인트는 이제 그 상태를 성공(HTTP 200)으로 보고하지 않습니다.
>
> **중요 — 임금일지 접근권한:** 현재 앱은 닉네임/비밀번호 로그인과 Firebase 익명 인증을 함께 사용합니다. `work_logs` 규칙은 문서의 `workerId` 형식은 검사하지만, 해당 workerId와 인증 UID가 같은 소유자인지 연결하지 않습니다. 클라이언트의 workerId 필터만으로는 보안 경계가 되지 않습니다. 소유권 연결과 타인 기록 읽기 거부 테스트가 적용되기 전까지 임금일지를 UID 기준으로 보호한다고 간주하지 마세요. 규칙을 단순히 관리자 전용으로 바꾸면 일반 근로자의 기능이 깨지므로, 인증·데이터 이전 설계와 함께 별도 변경해야 합니다.

`/api/health`는 함수와 런타임 상태 확인용이지 전체 앱의 사용자 동선을 보증하는 테스트가 아닙니다. 일일 보고서의 PASS 수도 앱 기능 전체의 실사용 검증으로 해석하지 않습니다. 실제 터미널 데이터 변화와 필드 채움률은 주간 자가 점검 결과에서 확인합니다.

## 2. 일일·주간·월간 확인

### 매일 (약 5분)

1. `reports/latest.md`에서 종합 판정, WARN/FAIL, 점검 시각을 확인합니다.
2. GitHub Actions의 일일 점검과 시간별 스케줄 감시가 성공했는지 확인합니다.
3. Vercel Cron 로그에서 일일 점검·DB 정리 결과를 확인합니다.
4. 메일 상태가 `sent`, `skipped`, `failed` 중 무엇인지 확인합니다. `skipped`는 메일 자격증명이 없거나 발송이 꺼진 경우일 수 있습니다.
5. 선박 스케줄의 기준 시각이 최신인지 운영 화면에서 확인합니다.

### 매주 (약 15분)

1. `reports/self-check/latest.md`의 미해결 FAIL, 데이터 드리프트, 자동 복구 및 재검증 결과를 확인합니다.
2. 8개 터미널의 수집량·핵심 필드 채움률이 기준선과 크게 달라졌는지 확인합니다.
3. 백업 API 응답에서 `ok: true`, `persistent: true`, `backupObjectPath`가 모두 있는지 확인합니다.
4. GCS 버킷에 해당 객체가 실제로 존재하는지 별도 권한으로 확인합니다. 객체 생성 성공만으로 복구 가능성이 증명되지는 않습니다.

### 매월 (약 30분)

- Vercel·Firestore·Storage 비용과 Firestore 읽기량의 추세를 확인합니다.
- 관리자 계정, 서비스 계정 권한, 외부 연동 자격증명 및 사용하지 않는 환경변수를 검토합니다.
- 보고서 보존 정책을 점검합니다. 일일 산출물은 Git에서 계속 누적되므로, 이력 보존 요구와 저장소 증가를 함께 검토합니다.

### 분기별 복구 훈련

- 운영과 분리된 테스트 프로젝트/환경에 백업을 복원합니다.
- 복원된 문서 수와 표본 문서 필드를 원본 백업의 `counts`와 비교합니다.
- 성공/실패, 소요 시간, 복구 절차에서 막힌 부분을 기록합니다.
- 사용자 원본 데이터를 운영 컬렉션에 시험 복원하지 않습니다.

## 3. Vercel 주간 백업 영구 보존 설정

저장소 코드는 `FIRESTORE_BACKUP_BUCKET`이 설정된 경우 전용 GCS 버킷으로 JSON 백업을 올립니다. 버킷 생성과 IAM 설정은 Google Cloud/Vercel 콘솔에서 운영자가 완료해야 합니다.

**현재 백업 범위는 Firestore 전체가 아닙니다.** 코드의 `BACKUP_COLLECTIONS`에 지정된 `work_logs`, `ships`, `posts` 세 컬렉션만 덤프하며, 다른 컬렉션(설정·공지·알림 등)과 Firebase Storage의 사진 파일은 포함하지 않습니다. 전체 재해 복구를 목표로 한다면 보존 대상 컬렉션과 Storage 객체 백업을 별도로 확정하고, 복원 도구·테스트를 추가해야 합니다.

1. `busan-hak-port` 프로젝트에 백업 전용 Google Cloud Storage 버킷을 만들고 Cloud Storage API가 활성화되어 있는지 확인합니다.
2. **Public access prevention**과 **Uniform bucket-level access**를 활성화하고, 공개 읽기 권한을 부여하지 않습니다.
3. Vercel 런타임이 사용하는 Firebase Admin 서비스 계정에 해당 버킷의 `Storage Object Creator` 역할만 부여합니다. 별도 복구 담당 계정에는 필요한 경우에만 읽기 권한을 줍니다.
4. 버킷에 보관 기간(예: 8~12주)을 정한 Lifecycle 정책을 설정합니다. 저장소 코드는 Cloud 객체를 자동 삭제하지 않습니다.
5. Vercel Production 환경 변수에 `FIRESTORE_BACKUP_BUCKET=<버킷 이름>`을 등록하고 재배포합니다. `.env.example`에 설명이 있습니다.
6. 수동으로 `GET /api/cron/weekly-backup`을 `Authorization: Bearer <CRON_SECRET>` 헤더와 함께 호출해, JSON에서 `ok: true`, `persistent: true`, `backupObjectPath`를 확인합니다.
7. GCS에서 해당 객체의 존재·크기를 확인하고, 이후 분기별 복구 훈련을 수행합니다.

버킷 미설정 시 Vercel API는 HTTP `503`과 `error: "persistent_backup_bucket_not_configured"`를 반환합니다. 업로드 실패는 성공으로 위장하지 않고 HTTP `500` 오류로 반환합니다. 서비스 계정 키는 저장소, 보고서, 채팅에 기록하지 않습니다.

## 4. 코드 변경·배포 절차

1. 기능 변경은 현재 작업 브랜치에서 진행하고, PR에서 변경 범위·Firestore 규칙·색인·환경변수 영향을 검토합니다.
2. 로컬에서 `npm ci`, `npm run check`, `npm run test:rules`를 실행합니다. 규칙 변경 시 허용·거부 케이스를 모두 확인합니다.
3. Preview/테스트 환경에서 대표 동선을 점검합니다. 최소한 앱 로드, 스케줄, 임금 계산 경계, 테스트 계정의 일지 저장·재조회, 관리자 기능 권한을 포함합니다.
4. 승인 후 공식 운영 대상인 Vercel에 배포합니다. Firestore 규칙/색인 변경은 앱 코드와 같은 배포 계획 안에서 적용하고, 이전 버전 호환 여부를 검토합니다.
5. 배포 직후 `/api/health`와 실제 대표 동선을 확인합니다. `200` 응답 하나만으로 릴리스를 완료 처리하지 않습니다.
6. 문제가 있으면 배포 이력에서 직전 정상 버전으로 되돌리고, 데이터 규칙을 변경했다면 롤백 순서와 하위 호환성을 별도로 확인합니다.

현재 Firebase Hosting(`busan-hak-port.web.app`)은 레거시 배포 경로로 문서화되어 있습니다. 공식 주소를 하나로 유지하고, 기존 주소의 리다이렉트/중단은 Firebase/Vercel 콘솔 권한이 있는 운영자가 별도 검증 후 수행해야 합니다.

## 6. 보안·데이터 취급 원칙

- PIN, `CRON_SECRET`, Firebase 서비스 계정 키, 메일 자격증명은 코드·이슈·보고서·채팅에 붙이지 않습니다.
- 화면 잠금은 UI 게이트입니다. 실제 권한은 Firebase Authentication과 `firestore.rules`가 강제해야 합니다.
- 임금일지 보안 완료 조건은 “클라이언트에서 본인만 조회”가 아니라, **에뮬레이터에서 타인 UID/계정의 읽기·목록 조회가 거부됨**을 증명하는 테스트입니다.
- 현재 로그인 구조는 닉네임 기반이므로 UID 소유권 도입은 계정/기기 변경 흐름과 기존 문서 이전을 함께 설계합니다. 규칙만 급히 바꿔 기존 사용자 접근을 끊지 않습니다.
- 운영자 자가 복구는 파생 캐시·보고서·상태 데이터에 한정하고, 근무일지·게시글 등 사용자 원본 데이터를 자동 수정·삭제하지 않습니다.

## 7. 의존성 보안 점검

- 릴리스 전 `npm audit --omit=dev`로 운영 의존성을 확인하고, 정기적으로 `npm audit`로 개발·테스트 도구도 확인합니다.
- 잠금 파일은 `npm ci`로 재현 검증하고 `npm run check`와 `npm run build`를 통과시킵니다.
- `npm audit fix --force`는 주요 버전 변경과 테스트 도구 다운그레이드를 일으킬 수 있으므로 자동 실행하지 않습니다. 남은 취약점은 패키지 경로·운영 노출 여부·호환 가능한 수정 버전을 검토해 별도 변경으로 처리합니다.

## 8. 추적할 운영 지표

초기 목표는 측정 기준을 확정한 뒤 조정합니다.

- CI/규칙 테스트: PR 병합 전 필수 통과 100%; 규칙 에뮬레이터 미실행을 통과로 취급하지 않음.
- 스케줄 신선도: 성공 수집 시각과 출처를 사용자에게 표시하고, 예상 주기 2회 이상 누락 시 조치.
- 백업: 주 1회 영구 업로드, 매월 객체 확인, 분기별 복구 성공.
- 장애 발견: 일일 자동 점검 실패가 Actions 결과에 드러나고 보고서/아티팩트가 남음.
- 보안: 타인 근무일지 읽기 거부 테스트와 관리자 접근 테스트를 규칙 변경마다 수행.
